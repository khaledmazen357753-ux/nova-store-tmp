# قاعدة البيانات — Turso (libSQL)

## لماذا تغيّر المحرك؟

كان المشروع يستخدم `node:sqlite` بملف على القرص. محلياً يعمل بشكل ممتاز،
لكن على Vercel نظام الملفات **للقراءة فقط** ولا يسمح بالكتابة إلا في `/tmp`،
و`/tmp` يُمسح مع كل إعادة تشغيل. النتيجة: أي فاتورة أو قيد يُدخله المستخدم
يضيع بعد فترة خمول، والبيانات ترجع للأرقام الأولية.

الحل: **libSQL** — نفس محرك SQLite (نفس الـ SQL تماماً)، لكنه يدعم
الاتصال بقاعدة **Turso** سحابية دائمة مع الاحتفاظ بنسخة محلية للسرعة.

## كيف يعمل

```
   طلب المستخدم
        │
        ▼
  ┌──────────────┐   قراءة/كتابة فورية (متزامنة، سريعة)
  │ نسخة محلية   │◄──────────────┐
  │  SQLite      │               │
  └──────────────┘               │
        │                        │
        │ مزامنة بعد كل كتابة    │ نفس كود الاستعلامات
        ▼                        │ (235 استعلاماً، لم تُلمس)
  ┌──────────────┐               │
  │    Turso     │───────────────┘
  │  (دائمة)     │
  └──────────────┘
```

المهم: **لم يُعدَّل أي استعلام**. الطبقة الجديدة (`src/libsql-adapter.js`)
تقدّم نفس الواجهة بالضبط: `db.exec()`، `db.prepare().get()/.all()/.run()` —
كلها متزامنة كما كانت.

## الإعداد (خمس دقائق، مرة واحدة)

### 1) أنشئ قاعدة على Turso

```bash
# تسجيل الدخول (مرة واحدة)
turso auth signup        # أو turso auth login

# إنشاء القاعدة — اختر أقرب منطقة لك
turso db create plus-erp --location mad     # مدريد (الأقرب لمصر)
```

> المناطق المتاحة: `mad` (مدريد) · `fra` (فرانكفورت) · `ams` · `iad` · `sin`
> اختر `mad` أو `fra` لأقل زمن استجابة من مصر.

### 2) احصل على الرابط والتوكن

```bash
turso db show plus-erp --url
# → libsql://plus-erp-xxxx.turso.io

turso db tokens create plus-erp
# → eyJhbGciOi...
```

بدون تثبيت CLI؟ من [لوحة Turso](https://turso.tech) → اختر القاعدة →
**Connect** → ستجد الرابط والتوكن جاهزين.

### 3) اضبط المتغيّرات على Vercel

من لوحة Vercel → مشروع `plus-erp-api` → **Settings** → **Environment Variables**:

| الاسم | القيمة |
|---|---|
| `TURSO_DATABASE_URL` | `libsql://plus-erp-xxxx.turso.io` |
| `TURSO_AUTH_TOKEN` | التوكن |

اختر **Production** و **Preview** و **Development**، ثم **Redeploy**.

### 4) (اختياري) ارفع بياناتك الحالية

لو عندك بيانات محلية تريد نقلها — مرة واحدة فقط:

```bash
cd plus-backend
TURSO_DATABASE_URL="libsql://..." TURSO_AUTH_TOKEN="..." npm run migrate:turso
```

لو القاعدة فارغة، التطبيق يزرع البيانات الأولية تلقائياً عند أول تشغيل —
**لا تحتاج هذه الخطوة**.

## التحقق

```bash
# على الخادم المنشور
curl https://plus-erp-api.vercel.app/api/health
```

الرد يجب أن يحتوي:
```json
{
  "ok": true,
  "storage": "turso",        ← المهم: turso وليس local-sqlite
  "driver": "libsql",
  "persistent": true          ← true = البيانات دائمة
}
```

لو ظهر `"storage": "local-sqlite"` أو `"persistent": false`، فالمتغيّرات
لم تُضبط أو لم يُعمل Redeploy بعد.

### اختبار شامل محلي

```bash
cd plus-backend
npm start                  # في نافذة
npm run verify             # في نافذة أخرى
```

يغطي 38 نقطة: التقارير الستة، دليل الحسابات، البيانات الأساسية،
عملية كتابية كاملة، **والتوازن المحاسبي بعد كل خطوة**.

## الصلابة (ماذا يحدث لو تعطّلت Turso؟)

| السيناريو | السلوك |
|---|---|
| Turso غير مضبوط أصلاً | يعمل محلياً بملف SQLite — ممتاز للتطوير |
| Turso متعطّل وقت الإقلاع | **الخادم يقلع عادي** على النسخة المحلية + تحذير في اللوج |
| الشبكة انقطعت أثناء العمل | العمليات تُحفظ محلياً، والمزامنة التالية تدفعها |
| فشل `sync()` | لا يُفشل طلب المستخدم — يُعاد المحاولة في الكتابة التالية |
| وحدة `libsql` غير متاحة | تحوّل تلقائي إلى `node:sqlite` (بلا استمرارية سحابية) |

> **لا توجد نقطة فشل واحدة.** أي عطل في Turso يُنزل النظام لوضع "يعمل
> بلا استمرارية سحابية" — لا إلى التوقف.

## الملفات المعنية

| الملف | الدور |
|---|---|
| `src/libsql-adapter.js` | طبقة التوافق: نفس واجهة `node:sqlite` فوق libSQL + إزالة `_metadata` |
| `src/db.js` | اختيار نمط التخزين وفتح القاعدة |
| `src/server.js` | مزامنة تلقائية بعد كل عملية كتابة + تشخيص في `/api/health` |
| `scripts/push-to-turso.js` | ترحيل البيانات المحلية إلى Turso (مرة واحدة) |
| `scripts/verify-turso.js` | اختبار توافق شامل (38 نقطة) |
| `vercel.json` | تضمين ملفات libSQL الأصلية في حزمة الدالة |
